Claude Code 会把什么发出去？

我查了一下 Claude Code 有没有读取网卡 MAC、机器序列号，以及它在模型请求之外还会发送哪些数据。

检查的安装包是 macOS arm64 版 2.1.280。本地另有 2.1.197 到 2.1.220 留下的失败记录，可以对照里面的字段，但不能当作 2.1.280 的运行结果。安装包哈希和复核方法在文末。

本地留下了哪些记录

在 ~/.claude/telemetry/ 里，我找到了 8 个失败事件文件，一共 173 条记录。它们共用一个设备 ID，其中 53 条带有账户和组织 UUID，37 条带有 Git HEAD SHA。附加字段里的 additional_metadata 是 Base64 编码的 JSON，解开后能看到提示词长度、耗时、hook 名、模型提供商和操作分类。Base64 只是编码，不提供加密保护。

配置里的 userID 由密码学随机数生成，保存在 ~/.claude.json 中。多条遥测记录会复用同一个值，进入 Anthropic 事件时的字段名是 device_id。另一个字段 machineID 也来自随机字节；查到的这两条生成路径都没有用到 MAC 或序列号。Datadog 错误记录会取 machineID 的前 12 个字符，模型 API 的 metadata.user_id 也包含设备和会话层标识。

这些文件属于发送失败队列，能证明客户端生成并缓存过相应事件。我没有拿到对应时段的网络记录，不知道哪些后来重试成功、哪些一直没有发出去。

换了 API 地址，其他请求怎么办

你交给 Claude Code 的问题，以及进入模型上下文的代码和工具结果，会随模型请求发到所用的服务端。关闭遥测不会停止这部分任务通信，官方数据使用说明也有说明。

在我检查的版本中，额外的使用事件会走 Anthropic 的事件批次接口；一部分事件和错误报告还有 Datadog 出口。它们分别有提供商、凭据、采样和禁用开关等条件。当前官方网络文档也列出了两个 Datadog 接收地址，分别用于运行事件和错误报告。

OpenTelemetry 的接收地址可以由用户或组织的托管设置配置。启用导出器后，数据发往这个地址。它与 Anthropic 自己的运行遥测分开，具体配置见官方监控文档。

在 2.1.280 已查到的核心遥测判断里，ANTHROPIC_BASE_URL 没有被直接用作禁用条件。把它改成第三方地址后，仍需分别检查 Anthropic 事件和 Datadog 日志的发送条件。自定义地址对凭据和最终发送的影响，这次没有全部追完。

事件里有没有代码和提示词

提取 JavaScript 模块后，我按字面量事件名做了统计：2,603 个调用点，覆盖 1,713 种事件名，分布在 261 个模块里。这是静态代码统计，实际会话会触发哪些事件，取决于功能、配置和操作。动态生成的名称不在统计里，展开运算符带来的字段也需要人工回溯。

内置 telemetry 插件的接口会拒绝自由文本字符串，只接受布尔值、有限数字和列举值。核心事件则由各个调用者处理参数。我检查过的 Bash 事件会把命令转成类别、白名单程序名和结构特征；API 错误事件记录受限错误类型、状态和重试次数；一些工具异常事件会清洗错误消息，转成哈希或堆栈特征。已检查的几个 paths 字段装的是计数或枚举，没有传路径原文。

对那 173 条旧记录做绝对路径、邮箱和令牌形态扫描，没有发现匹配值。已检查的代码也没有支持“默认遥测会额外发送完整提示词、源文件正文和原始 Bash 命令”的证据，但我没有逐个核完上千种事件的全部字段。

Datadog 的事件镜像会先删一组敏感字段，再规范化工具、模型和 HTTP 状态；错误上报会清洗异常消息和堆栈，并限制单进程的排队数量。这些清洗规则不能保证识别用户自定义的所有秘密。安装包里虽然有 sentry.io 字符串，但沿 logError 追到 POST，这版 CLI 的这条错误上报路径实际指向 Datadog。

OpenTelemetry 的 OTEL_LOG_USER_PROMPTS 默认关闭；开启它并配置相应导出器后，提示词原文可以进入指定的监控接收端。当前官方文档另列出默认关闭的 OTEL_LOG_RAW_API_BODIES，用于记录包含对话历史的模型 API 请求和响应 JSON。内联模式受内容长度限制；文件模式把未截断内容写到本地文件，事件里记录文件引用。是否外发、外发多少，要看导出配置。

机器码读取与旧版日期标记

在提取出的 JavaScript 里，我没有找到常见的 MAC、机身序列号读取调用。OpenTelemetry 组件中有通过 ioreg 读取 IOPlatformUUID 的代码，读取结果是否外发取决于资源检测和 OTLP 导出链是否生效。本次普通本机会话中，没有看到已配置的 OTLP 目标。

hostname 出现在监控资源检测、远程控制设备名等几处用途里。本机网卡 IP 与接收端从连接上看到的来源 IP 也需要分开检查。包内有截屏、输入和录音相关原生扩展，我没有发现它们后台自动录制并通过默认遥测上传的证据。这三个扩展未完成机器码级审计，本文结论不覆盖它们的全部行为。

2026 年 6 月，Claude Code 官方仓库的一条用户报告展示过旧版本的异常：系统提示词的日期行会根据自定义 API 主机名换用视觉相近的撇号，某些时区还会改变日期分隔符。这是用户提交的复现报告，不能当作官方对用途的确认。

报告里的变化出现在发给模型的系统提示词中，没有走独立遥测字段。我回看了 2.1.280 的日期行构造，用的是普通 ASCII 撇号和 YYYY-MM-DD，没有找到旧报告中的字符选择逻辑。这次只检查了这一份 macOS 安装包，其他版本需要另查。

遥测开关和出站检查

检查当天，本机缓存里有 700 个 GrowthBook 远程功能标志。其中一条远程控制路径会在相应标志关闭后停止服务，本地遥测禁用条件则在另一条检查链上。700 个是当天的缓存数量，其含义没有逐项审完；这份缓存也没有证明服务端能绕过本地遥测禁用开关。

按照截至 2026 年 9 月 24 日的官方数据使用文档，可以用下面的命令启动一个关闭非必要流量的会话：

CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 claude

需要分别控制时，使用指标和错误报告各有 DISABLE_TELEMETRY=1、DISABLE_ERROR_REPORTING=1。关闭遥测或非必要流量还会影响 Remote Control 依赖的功能标志求值。

WebFetch 的域名安全检查有独立开关 skipWebFetchPreflight，不会随上述总开关关闭；关掉它会放弃这层安全检查。当前官方文档还列出官方插件市场自动安装的独立退出开关。上述命令不会阻止全部出站请求。

团队环境需要同时检查 OpenTelemetry 的接收地址和托管设置，因为导出配置可能由组织下发。需要限制出站连接时，可以按官方网络文档逐项核对目的地，再通过网关或防火墙限制，并用受控测试检查实际请求。

公开排查记录前，记得去掉凭据和标识符。不要直接上传完整的 ~/.claude.json、遥测队列或抓包文件。

检查范围、安装包哈希与复核方法

本次静态检查对象是 macOS arm64 版 Claude Code 2.1.280，安装文件 SHA-256 为 387a5c5dcdbb815085edf0baf79591f9d8894efe922bceaf3d75b1b08055229d。本机观察发生在 2026 年 9 月，升级版本后要重新检查。

我先用字节搜索查找 IOPlatformUUID、networkInterfaces 和时区字符串，再解析 Bun 单文件程序里的模块图，从提取出的 JS 模块追调用链。字节搜索可能漏掉其他写法或编译到别处的实现，不能仅凭没有命中就认定某项功能不存在。

模块图里有 37,884,508 字节可读的 JS 源文本，附着 82,505,096 字节字节码。提取出的 1,991 个 JavaScript 模块全部通过语法解析。文件名多是 chunk-xxxxxxxx.js，函数名也经过压缩，没有随包源码映射，但事件名、上报地址、字段名和关键分支仍能读出来。Bun 官方文档也说明，启用字节码编译不会因此隐藏源码。

复核时先核对安装包哈希、签名和 Bun 段，再按模块图提取 JS。直接按固定偏移截取二进制可能混入非源码字节；本次使用的偏移量只适用于这一个安装包。

CC="$HOME/.local/share/claude/versions/2.1.280"
shasum -a 256 "$CC"
codesign -dv --verbose=2 "$CC"
otool -l "$CC" | rg -A8 'sectname __bun|segname __BUN'

在提取出的模块中，chunk-m200zvyg.js 有核心事件序列化和 Datadog 镜像，chunk-h8651pre.js 有内置 telemetry 插件，chunk-s8swgzep.js 有错误上报条件。模块名会随版本变化，所以先核安装包哈希，再核调用链。

本文没有对应会话的 TLS 明文抓包，没有逐指令审计 Bun 运行时及三个原生扩展，也没有服务端接收和保存记录。
