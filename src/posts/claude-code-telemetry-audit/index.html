X-Ray · Agent 工具链

拆开 Claude Code 2.1.280，看看它读了什么，又把什么发出去

我原先问的是一个很直的问题。Claude Code 能读我的代码、运行命令，那它会不会顺手读网卡 MAC、机器序列号和 IP？沿着这个问题查下去，我翻了本机的二进制、旧遥测队列和一整段 Claude Code 调研记录。最后发现，最需要解释清楚的地方，是“程序里有读取能力”“事件在本机被构造”“服务端实际收到数据”之间那几步。

这篇只针对我检查的 macOS arm64 安装包 2.1.280。安装文件 SHA-256 为 387a5c5dcdbb815085edf0baf79591f9d8894efe922bceaf3d75b1b08055229d。文中的本机观察发生在 2026 年 9 月，升级版本后要重新检查。

先把安装包打开

起初我用字节搜索找 IOPlatformUUID、networkInterfaces 和时区字符串。这能迅速定位疑点，却不适合给出“全部代码都没有”的结论。一个字符串没搜到，可能是代码写法不同，也可能被编译到了别处。后来我们直接解析了 Bun 单文件程序里的模块图，再从提取出的 JS 模块追调用链。

模块图里有 37,884,508 字节可读的 JS 源文本，还附着 82,505,096 字节字节码。代码确实难看，文件名多是 chunk-xxxxxxxx.js，绝大多数函数名短到一两个字符，也没有随包源码映射。但事件名、上报地址、字段名和关键分支仍能在源文本里读出来。Bun 自己也说明，字节码不会因此遮住源码。这种打包和压缩妨碍阅读，却不足以证明整套采集逻辑被深度加密。三个随包的原生扩展没有逐指令反编译，我把它们留在结论的边界里。

想自己复核这一版，可以从这里开始

先确认拿到的是同一份安装包。按固定位置截取二进制做粗搜，会把非源码字节混进结果。先查签名、哈希和 Bun 段，再按模块图提取 JS；偏移量只对这一个安装包成立。

CC="$HOME/.local/share/claude/versions/2.1.280"
shasum -a 256 "$CC"
codesign -dv --verbose=2 "$CC"
otool -l "$CC" | rg -A8 'sectname __bun|segname __BUN'

在提取出的模块中，chunk-m200zvyg.js 有核心事件序列化和 Datadog 镜像，chunk-h8651pre.js 有内置 telemetry 插件，chunk-s8swgzep.js 有错误上报门控。模块名会随版本变化，所以先核安装包哈希，再核调用链。

一段 Claude Code 会话，有几条不同的出站路

Claude Code 一次会话可能通过多条路径与外部通信。模型请求携带完成任务所需的对话和工具结果；Anthropic 一方事件、Datadog 日志、按配置启用的 OpenTelemetry，以及 WebFetch 的域名预检，各有自己的触发条件。要判断程序额外记录了什么、发往哪里，得沿每条路径分别看字段、门控和发送代码。

把 ANTHROPIC_BASE_URL 指向第三方，不能据此认定一方遥测会自动停止。2.1.280 的核心遥测门控检查提供商模式、网关、自定义 OAuth 和本地禁用开关，没有直接拿这个 URL 当总闸。自定义地址如何影响凭据和最终发送，还得继续追调用链；模型请求改了目的地，不能替另一条遥测路径下结论。

随机设备 ID 没有硬件来源，依然能把事件串起来

在用户配置里，userID 是一个持久标识。我们追到的生成路径用密码学随机数，没有把 MAC、序列号或主板 UUID 混进去。配置里另一个名字更吓人的 machineID，在这条生成路径里同样来自随机字节；Datadog 错误记录会取它的前 12 个字符。userID 进入一方事件时叫 device_id，模型 API 的 metadata.user_id 也包含设备和会话层标识。随机生成只说明生成方式；它被保存并重复使用以后，仍然能关联同一安装的多次活动。账号登录后出现的账户 UUID、组织 UUID，则是另一层身份。

本机 ~/.claude/telemetry/ 留着 8 个失败事件文件，共 173 条，来自 2.1.197 至 2.1.220。173 条共用一个设备 ID，53 条带账户和组织 UUID，37 条带 Git HEAD SHA。它们的 additional_metadata 是 Base64 编码的 JSON，解开能看见提示词长度、耗时、hook 名、提供商和操作分类等字段。这批样本说明客户端曾生成并缓存这些记录，文件名中的“failed”也提醒我，它们不能证明服务端已经收到。

事件多到不能靠一句“只记操作类型”概括

这次把 1,991 个 JS 模块都交给语法解析器，零解析错误。按字面量事件名统计，i(...) 形式的调用点有 2,603 处，覆盖 1,713 种事件名。它们分布在 261 个模块里。这里的统计仍会漏掉动态生成的名称，展开运算符带来的字段也得人工回溯。

这两套约束不能混用。插件主动拒绝自由文本，但核心事件还有大量由调用者逐个处理的参数。已经回溯的 Bash 事件会把命令解析成类别、白名单程序名和结构特征；API 错误事件把受限错误类型、状态和重试次数放进字段；工具异常调用清洗函数，把消息变成哈希和堆栈特征。字段名叫 paths 也不必然意味着传了路径，已检查的几个点实际上装的是计数或枚举。反过来，看到这几个点没有原始内容，也不能替剩下上千种事件作保证。

对那 173 条旧样本做绝对路径、邮箱、令牌形态扫描，没有发现匹配值。这个结果只说明这批文件里没有扫出这些形态，2.1.280 的核心事件仍须逐调用点检查。OpenTelemetry 还有独立开关 OTEL_LOG_USER_PROMPTS，默认把提示词记成 <REDACTED>，开启后会传原文。判断某类内容会不会外送，必须同时说清管线和启用条件。

Datadog 也有自己的出口。核心代码会把选定的一方事件再做一份日志，先删一组敏感字段，并规范化工具、模型和 HTTP 状态。另一个错误追踪路径把清洗后的异常消息、堆栈、版本和平台信息送到 Datadog。它有独立的开关与合规判断，还给单进程排队数量设了上限。清洗规则很长，我只把它称作尽力脱敏；任何正则表都不能保证识别用户自定义的所有秘密。安装包里也能找到 sentry.io 字符串，但沿 logError 到 POST 追完，2.1.280 的这条 CLI 错误上报路径实际指向 Datadog。

硬件这一块，读到哪里，走到哪里

我最在意的机器码问题，后来拆成了三问。程序能不能调用系统 API，代码里有没有这样的调用，调用结果是否进入出站载荷。macOS 用户态程序有能力读不少系统信息，所以“技术上能读”本身回答不了这台机器有没有被采集。

ioreg 读取 IOPlatformUUID 的调用点确实存在，位于随包的 OpenTelemetry 组件中。导出配置既可能来自用户环境，也可能由托管设置注入。对普通未配置的本机会话，我们没有看到 OTLP 目标已设置；对程序能力，只能写“条件成立时可能导出”。这张图保留了一个重要的空白，原生扩展未完成机器码级审计，因此本文不能宣布整台软件“硬件零指纹”。

我为什么还去查日期里的撇号

2026 年 6 月，Claude Code 官方仓库的一条公开 issue 展示过旧版本的异常。系统提示词里普通的日期行，会根据自定义 API 主机名换用视觉相近的撇号；某些时区还会改变日期分隔符。那是一个值得认真复验的旧机制，因为它没有走显眼的遥测字段。

最初的整段二进制扫描，Asia/Shanghai 和 Asia/Urumqi 是零命中。再把真正的 JS 模块提出来看，当前日期行保留普通 ASCII 撇号和短横线，没找到旧的字符选择调用链。这个结果与旧机制已经不在 2.1.280 的判断相符。它只覆盖本次检查的安装包，不能用“搜不到两个字符串”证明以后任何版本都不会用别的方式做环境分类。

现在的代码仍会读时区给终端时间显示或设置界面用，语言信息也会影响语音听写默认语言。日历日期可能出现在发给模型的系统上下文中。把这几件日常功能与旧版隐写并排看，区别就清楚了，读取本地时区、把完整时区上传、用时区改写日期标记，是三种不同的行为。

700 个远程标志说明了什么

聊天记录里我们后来又追了一条线。写作当天，本机缓存里有 700 个 GrowthBook 远程功能标志。数量是那天的缓存快照，不是这个版本永远固定的配置表。它们能改变一些功能参数、提示词开关和最低版本条件。远程控制的 deviceBridge 还有一段很直白的代码，标志刷新后门关了，它就打印 stopping: the gate turned off 并停掉服务。

远程标志能让本地功能改变状态，这一点有代码证据。它不能直接证明服务端能修改已经启动进程的环境变量，也不能保证所有远程标志都与遥测无关。已追到的一方事件门控会检查本地禁用条件；那 700 个标志的语义没有逐一审完。

现在我会怎样给这次调查下结论

2.1.280 的 JS 里有不少环境与行为信号，远比“只收一个匿名设备号”详细。稳定设备 ID、账户 UUID、会话 ID、Git 提交 SHA 和操作事件可以互相拼接。Datadog 与 Anthropic 事件接口也是独立出口。与此同时，已追到的代码没有支持“默认遥测偷偷发送完整提示词、源文件正文、原始 Bash 命令、屏幕或音频”这个判断。可选 OTEL 内容开关和屏幕音频功能各有自己的启动条件，需要按实际配置与运行行为再看。

最有用的复核动作很朴素。先固定要审计的版本与哈希，再看本地环境和托管设置，接着沿事件构造走到发送函数。如果要回答“这台机器那晚究竟发了什么”，还得拿到对应时段的网络证据；旧失败队列只能补一部分。读者自己检查配置时，别把 ~/.claude.json、遥测队列或抓包里的凭据和标识符整份贴到网上。

本文复核了提取出的 JS、旧版失败队列和原始调研记录。没有真实 TLS 明文抓包，也没有逐项反编译 Bun 运行时与三个原生扩展。代码里有发送路径、本地缓存过事件、远端实际收到并保存，是三个不同的结论。
