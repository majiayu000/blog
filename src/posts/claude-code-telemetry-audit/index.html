X-Ray · Agent 工具链

Claude Code 会把什么发出去？

我一开始只想确认一件事：Claude Code 会不会读取我的机器码。

它能看代码、执行命令，当然有机会接触电脑上的其他信息。我想知道的是，它有没有读取网卡 MAC、机器序列号，或者拿这些东西生成一个可以长期识别我的编号。于是我翻了本机的安装包，也看了它留在磁盘上的遥测记录。

查到后面，最值得注意的反而是一个随机生成的 ID。即使不用机器序列号，只要这个 ID 一直保留，程序就有办法把不同时间的使用记录联系起来。围绕这个 ID，我又看到了账户标识、会话标识、Git 提交信息，以及几条分别控制的上报路径。

这篇记录的是 macOS arm64 版 Claude Code 2.1.280 的检查结果。用来对照的本地失败队列来自更早的版本，具体范围会在下面说明。安装包哈希、检查方法和没有覆盖的部分，放在文末供复核。

先从电脑里留下的 173 条记录说起

在 ~/.claude/telemetry/ 里，我找到了 8 个失败事件文件，一共 173 条记录，来自 2.1.197 到 2.1.220。它们共用一个设备 ID，其中 53 条带有账户和组织 UUID，37 条带有 Git HEAD SHA。附加字段里的 additional_metadata 是 Base64 编码的 JSON，解开后能看到提示词长度、耗时、hook 名、模型提供商和操作分类。Base64 在这里是编码，看起来不直观，但不提供加密保护。

这批记录让我把注意力从“机器码”转到了“关联”。我沿着配置里的 userID 查下去，看到它由密码学随机数生成，保存在 ~/.claude.json 中，进入 Anthropic 的事件时使用的字段名是 device_id。另一个叫 machineID 的值，在查到的生成路径里也来自随机字节。名字听起来像硬件指纹，实际没有用到 MAC 或序列号。Datadog 错误记录会取它的前 12 个字符；模型 API 的 metadata.user_id 也包含设备和会话层标识。

随机生成不代表每次都会换。一个编号只要持续复用，就能成为多次活动之间的连接点；再叠加账户和会话标识，记录之间的关系会更清楚。假如我关心的是自己的使用过程能被关联到什么程度，只问“有没有读机器序列号”，就漏掉了这部分。

还要交代这批文件的性质：它们是失败队列，只能证明客户端生成并缓存过这些事件。我没有拿到相应时段的网络证据，因此不知道其中哪些后来重试成功。它们也不能充当 2.1.280 的运行抓包。

换了 API 地址，其他请求怎么办

要看懂这些记录，先得把模型调用和产品遥测分开。你交给 Claude Code 的问题，以及进入模型上下文的代码和工具结果，会随着模型请求发到所用的服务端。关闭遥测以后，这部分任务通信仍然需要发生。官方数据使用说明也明确写着，本地运行的 Claude Code 需要通过网络与模型交互。

在我检查的版本中，额外的使用事件会走 Anthropic 的事件批次接口；一部分事件和错误报告还有 Datadog 出口。它们分别有提供商、凭据、采样和禁用开关等条件。当前官方网络文档也列出了两个 Datadog 接收地址，分别用于运行事件和错误报告。

OpenTelemetry 又是一套独立的监控配置。启用导出器后，数据发往指定的接收端，地址可以由用户或组织的托管设置配置。它与 Anthropic 自己的运行遥测分开，官方监控文档说明了这两套配置的区别。

所以，我不建议看到 ANTHROPIC_BASE_URL 换成了第三方地址，就直接认定“所有数据都只去这个地址”。在 2.1.280 查到的核心遥测判断中，这个 URL 没有被直接用作关闭遥测的总开关。它对认证和最终发送还有其他影响，需要接着追；仅凭模型请求改道，还回答不了日志和使用事件的去向。

对公司内部接入来说，我会分别检查模型请求、产品遥测和自建监控，而不把一个 API 地址当成整套程序的网络配置。

事件很多，里面有没有代码和提示词

提取 JavaScript 模块后，我按字面量事件名做了统计：2,603 个调用点，覆盖 1,713 种事件名，分布在 261 个模块里。这是代码中识别出的事件种类，不能读成“一次会话会发送 1,713 条记录”；哪些分支会执行，还要看功能、配置和实际操作。动态生成的名称不在这个统计里，展开运算符带来的字段也得人工回溯。

这些事件的字段约束也不完全相同。内置 telemetry 插件的接口会拒绝自由文本字符串，只接受布尔值、有限数字和列举值。核心事件则有大量由调用者各自处理的参数。我检查过的 Bash 事件，会把命令转成类别、白名单程序名和结构特征；API 错误事件会记录受限错误类型、状态和重试次数；一些工具异常事件会对错误消息做清洗，转成哈希或堆栈特征。甚至有些叫 paths 的字段，装的也是计数或枚举。光看名字，很容易判断错。

对那 173 条旧记录做绝对路径、邮箱和令牌形态扫描时，我没有发现匹配值。已经追到的代码，也不足以支持“默认遥测会额外发送完整提示词、源文件正文和原始 Bash 命令”这个说法。不过，我没有逐个确认上千种事件的全部字段，不能把几个清洗得比较仔细的调用点当成整套系统的保证。

Datadog 两条路径也有各自的处理。事件镜像会先删一组敏感字段，再规范化工具、模型和 HTTP 状态；错误上报会清洗异常消息和堆栈，并限制单进程的排队数量。我把这些称作尽力脱敏：清洗规则再长，也很难识别用户自定义的所有秘密。安装包里虽然有 sentry.io 字符串，但沿 logError 追到 POST，这版 CLI 的这条错误上报路径实际指向 Datadog。

OpenTelemetry 则允许配置内容记录。OTEL_LOG_USER_PROMPTS 默认关闭；开启它，并配置相应导出器后，提示词原文可以进入指定的监控接收端。补查当前官方文档时，我还看到默认关闭的 OTEL_LOG_RAW_API_BODIES，可记录包含对话历史的模型 API 请求和响应 JSON。内联模式受内容长度限制，文件模式则把未截断内容写到本地文件，事件里记录文件引用；是否外发、外发多少，还要看导出配置。因此，团队排查时得看内容记录选项，不能只问“有没有开遥测”。

机器码和时区，我查到了哪一步

回到最初的问题。在提取出的 JavaScript 里，我没有找到常见的 MAC、机身序列号读取调用。但 OpenTelemetry 组件中确实存在通过 ioreg 读取 IOPlatformUUID 的代码。它是否进入出站数据，取决于资源检测和 OTLP 导出链是否生效；本次普通本机会话中，我没有看到已配置的 OTLP 目标。

hostname 也出现在几处不同用途里，包括监控资源检测和远程控制设备名。至于 IP，“程序主动读取本机网卡地址”和“接收端看到网络连接的来源地址”是两件事。包内还有截屏、输入和录音相关原生扩展，但我没有据此发现后台自动录制并通过默认遥测上传的证据。这些扩展没有做完机器码级审计，所以这篇也不能给整个安装包开一张“从不读取硬件信息”的证明。

时区的检查还有一段背景。2026 年 6 月，Claude Code 官方仓库的一条用户报告展示过旧版本的异常：系统提示词里普通的日期行，会根据自定义 API 主机名换用视觉相近的撇号；某些时区还会改变日期分隔符。这类报告可以提供检查线索，但不能当作官方对用途的确认。

这个细节值得查，因为标记藏在正常发给模型的文字里，只盯着独立遥测请求会漏掉它。我回看了 2.1.280 的日期行构造，看到的是普通 ASCII 撇号和 YYYY-MM-DD，没有找到旧报告中的字符选择逻辑。这个结果针对本次 macOS 安装包，不能拿旧版本的发现直接替它下结论，也不能证明以后不会有新的实现。

查完以后，该怎么处理

这次检查让我觉得，判断隐私风险时，应该先把问题问具体：哪些数据会被记录，能否关联到同一安装或账户，什么条件下发送，发往哪里。把所有东西都叫作“匿名遥测”，或者反过来都叫作“偷数据”，都会漏掉决定结论的细节。

版本号以外，配置也值得留下记录。检查当天，本机缓存中有 700 个 GrowthBook 远程功能标志；其中一条远程控制路径，会在相应标志关闭后停止服务。这说明本地功能状态可以随远端配置变化。但这份缓存并没有证明服务端能够绕过本地遥测禁用开关，700 个标志的含义也没有逐项审完。

下面这部分依据的是截至 2026 年 9 月 24 日的官方数据使用文档，供实际配置时参考。要在终端中新启动一个关闭非必要流量的会话，可以这样运行：

CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 claude

需要分别控制时，使用指标和错误报告各有 DISABLE_TELEMETRY=1、DISABLE_ERROR_REPORTING=1。关闭遥测或非必要流量还会影响 Remote Control 依赖的功能标志求值，使用远程控制的人要留意这个影响。

不过，这条命令不等于断网。官方文档特别注明，WebFetch 的域名安全检查有独立开关 skipWebFetchPreflight，不会随上述总开关关闭；关闭它也意味着放弃这层域名安全检查。当前文档还列出官方插件市场自动安装的独立退出开关，因此不要把“非必要流量”理解为全部出站请求。

有团队监控的环境，还应核对 OpenTelemetry 的接收地址和托管设置。自己没有配置，不等于组织没有配置。要求严格控制出站连接的团队，我建议再用网关或防火墙验证允许的目的地，并结合受控测试确认实际请求。官方网络文档列出的连接用途可以用作检查起点，但不能拿一张域名表替代对实际环境的验证。

最后一个提醒比任何参数都简单：排查的时候，别把完整的 ~/.claude.json、遥测队列或抓包文件贴到公开平台。这些材料本身就可能包含需要保护的标识符和凭据。

我最初想找的是一个机器码，最后更在意的是那些能被长期连起来的使用记录。对我来说，了解它们如何生成、在哪里关闭、关闭后还有什么请求，比得到一个笼统的“安全”或“不安全”更有用。

检查范围、安装包哈希与复核方法

本次静态检查对象是 macOS arm64 版 Claude Code 2.1.280，安装文件 SHA-256 为 387a5c5dcdbb815085edf0baf79591f9d8894efe922bceaf3d75b1b08055229d。本机观察发生在 2026 年 9 月，升级版本后要重新检查。

起初我用字节搜索找 IOPlatformUUID、networkInterfaces 和时区字符串。这能定位疑点，却不适合给出“全部代码都没有”的结论：代码可能有不同写法，也可能被编译到了别处。后来直接解析了 Bun 单文件程序里的模块图，再从提取出的 JS 模块追调用链。

模块图里有 37,884,508 字节可读的 JS 源文本，附着 82,505,096 字节字节码。提取出的 1,991 个 JavaScript 模块全部通过语法解析。文件名多是 chunk-xxxxxxxx.js，函数名也经过压缩，没有随包源码映射，但事件名、上报地址、字段名和关键分支仍能读出来。Bun 官方文档也说明，启用字节码编译不会因此隐藏源码。

先确认拿到的是同一份安装包。按固定位置截取二进制做粗搜，会把非源码字节混进结果。先查签名、哈希和 Bun 段，再按模块图提取 JS；偏移量只对这一个安装包成立。

CC="$HOME/.local/share/claude/versions/2.1.280"
shasum -a 256 "$CC"
codesign -dv --verbose=2 "$CC"
otool -l "$CC" | rg -A8 'sectname __bun|segname __BUN'

在提取出的模块中，chunk-m200zvyg.js 有核心事件序列化和 Datadog 镜像，chunk-h8651pre.js 有内置 telemetry 插件，chunk-s8swgzep.js 有错误上报条件。模块名会随版本变化，所以先核安装包哈希，再核调用链。

本文没有对应会话的 TLS 明文抓包，没有逐指令审计 Bun 运行时及三个原生扩展，也没有服务端接收和保存记录。文中的本地队列、代码路径和官方配置说明分别回答不同的问题，不应混用。
