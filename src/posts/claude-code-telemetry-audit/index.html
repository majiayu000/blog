Claude Code 2.1.280 字节级审计：MAC、序列号零读取点，时区隐写确认已移除

2026 年 6 月底曝出时区隐写事件后，我不想靠转述了解手边这版 Claude Code 的底细，于是对 2.1.280 的二进制做了一次字节级审计。结论分三层：MAC 地址、机身序列号、本机 IP 在全部代码路径里没有读取点，主板 UUID 只剩一条默认关闭的 OTLP 通道；6 月的隐写管线确认已拔干净；远程特征标志系统则是活的——写作时本地缓存里有 700 个服务端标志，当天刚刷新。

审计对象：Claude Code 2.1.280（macOS arm64 原生二进制）。本文全部结论是 2026 年 9 月的时点快照，升级版本后需要重验。

为什么做这次审计

先把事件本身说清楚。2026 年 6 月底，社区研究者发现 Claude Code 曾在自定义 API 端点场景下读取系统时区、比对约 147 个中转域名，并把判定结果编码进系统提示词的日期格式和撇号码点——Asia/Shanghai 时区命中后日期分隔符从 - 变成 /，域名命中后 Today's 的撇号被换成 U+2019/U+02BC/U+02B9。这件事被 The Next Web、Reuters、TechCrunch 等广泛报道，Anthropic 工程师公开回应称这是 3 月上线的反转售实验、已在 7 月初的版本中移除。

报道归报道，我想要一份对当前版本的、可复现的字节级验证：隐写真的拔干净了吗？除了时区，它还读我机器上的什么？

审计方法

macOS 上的 Claude Code 是 Bun 编译的单文件二进制，JS 逻辑以明文区段嵌在其中，可以从固定偏移量切出来做全文扫描：

# 原生版安装路径（版本号即目录名）
CC=~/.local/share/claude/versions/2.1.280

# 内嵌 JS 区段约从 59MB 处开始，切出约 155MB
dd if=$CC of=/tmp/bundle.bin bs=1048576 skip=59

# 字节级搜索示例：硬件标识符、时区字符串、隐写码点
rg -a -c 'IOPlatformSerialNumber' /tmp/bundle.bin   # 0
rg -a -c 'Asia/Shanghai' /tmp/bundle.bin            # 0
rg -a -c 'os\.networkInterfaces' /tmp/bundle.bin    # 0

对低频疑点（比如 U+02BC/U+02B9 码点），需要用 Python 做上下文提取来定性——155MB 二进制里这些字节对天然会以指针表巧合的形式出现，必须看上下文才能区分真字符和编译产物。除静态扫描外，我还交叉验证了三类运行时证据：本地遥测队列的逐条解码（JSONL，可以自己看）、配置文件全字段枚举、系统级连接观测。

下文的结论分两种证据等级：能靠字节级扫描或本机数据解码直接复现的，正文直接给数字；由行为反推的，我会附上推理依据。

标识符是随机数，不是机器码

每次启动生成或读取的标识符全部是 crypto 随机值，持久化在 ~/.claude.json（明文，键名可自行查看）：userID（即每次请求携带的 device_id）是 32 字节随机 hex，生成代码里没有任何硬件输入；session_id 与 parent_session_id 每会话随机；登录后的 account_uuid / organization_uuid 来自 OAuth，属账户身份而非设备身份。

这意味着删掉配置文件里的这些值，它们就会重新随机生成。设备指纹意义上的硬件绑定，在标识符层不存在。

四条出站通道：一条无条件，两条有门控

通道目的地载荷门控
A · 模型 API 请求 跟随 ANTHROPIC_BASE_URL 对话内容 + 工具结果 + metadata.user_id{device_id, account_uuid, session_id} + 系统提示词内的本地日期 无条件，任何开关都拦不住
B · 遥测事件批量 硬编码 api.anthropic.com（不跟随 BASE_URL） tengu_* 事件 + 环境 21 键 + 进程指标 blob BASE_URL 指向第三方时自动停；CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC / DISABLE_TELEMETRY / DO_NOT_TRACK 可关
C · OTLP 导出 自行配置的端点 resource 属性含 host.id = IOPlatformUUID（主板 UUID）、host.name、host.arch 需同时设 CLAUDE_CODE_ENABLE_TELEMETRY=1 + OTEL_EXPORTER_OTLP_ENDPOINT，默认关
D · 基础流量 版本检查 / 会话校验 无遥测载荷 不受遥测开关影响

通道 A 是唯一无法关闭的出站：只要在用这个工具，对话内容和一个随机 device_id 就会进入发往模型端点的请求。这是产品形态决定的——模型必须收到内容才能工作。但有一点值得单独指出：metadata.user_id 在官方文档里并不显眼，而它不受任何遥测开关控制。

遥测事件里有什么、没有什么

把本地磁盘上的失败遥测队列逐条解码后，事件载荷的完整字段如下。有的部分：事件名、时间戳、session/account UUID、模型名、环境 21 键（platform、arch、shell、终端类型、运行时版本等）、进程指标（uptime、RSS、heap、物理内存大小、CPU 用时），以及行为字段——文件路径、bash 命令分类与 argv0、字节长度、权限决策。没有的部分：prompt 原文、文件内容、命令原文、hostname、用户名、locale、时区、任何硬件序列号。

一句话概括：它记录你做了什么类型的操作，不记录操作的内容。

机器码读取能力全清单

对读取点逐一定性之前要先立一个区分：能力（代码里有没有）不等于行为（实际读不读、发不发）。

读取目标代码读取点出口状态
主板 UUID ioreg -rd1 -c "IOPlatformExpertDevice" 仅 1 处（OTel SDK 的 getMachineId） 仅通道 C 休眠（默认无人配置）
hostname 3 处：OTel hostDetector（随通道 C）、设备名派生（1P 云功能）、本地同意记录绑定 前两者锁死或未启用，最后者纯本地 读而不发
MAC 地址 0（os.networkInterfaces 应用层零调用） — 不存在
机身序列号 0（连读取代码都没有） — 不存在
本机 IP 0（dgram 取 IP 技巧、ifconfig 自执行、IP 回声服务全查无） — 不存在
GPU / 电池 / GPS 0 — 不存在
出网探活 1 处：HEAD http://1.1.1.1（1 秒超时） 仅返回布尔连通性 无数据携带

两点说明。第一，macOS 上用户态进程读机器码毫无技术障碍——ioreg 不需要 sudo。所以能不能读的答案永远是能，有意义的结论只有当前代码里有哪些读取点、出口开着没有。这是信任问题，不是技术问题。第二，GCP/Azure 认证库内有一段云 VM 检测代码（/sys/class/dmi/... 路径、^42:01 MAC 前缀正则），在 macOS 上路径不存在，且仅在使用对应云凭证时才可能执行，判定结果是本地布尔值。

时区和语言：读了，但不出网

当前版本的读取点就两处，全是本地功能：Intl.DateTimeFormat().resolvedOptions().timeZone 用于终端 UI 时钟显示和 /config 时区设置；resolvedOptions().locale 提取语言码，仅用于语音听写（STT）的默认语言。process.env.LANG 与 LC_* 的读取次数为零。唯一出网的时区衍生物，是系统提示词里的本地日期——天粒度，随通道 A 发给你的模型端点。

服务端能控制本地到什么程度

这是最容易误解的一层，分两半说。

你设置的环境变量开关，服务端改不了，当前版本也绕不过。env 在进程启动时定格，OS 层没有任何远程修改通道；架构上本地优先——DISABLE_GROWTHBOOK 一设，远程标志求值系统整体瘫痪，官方报错文案明示了这一点。这部分是字节级可复现的。

但功能参数层确实受服务端实时控制。客户端内嵌了 GrowthBook 远程标志系统（默认端点 cdn.growthbook.io），写作时我的本地缓存里有 700 个标志、当天刚刷新过，控制范围包括各工具的输出 token 上限、最低版本要求（tengu_version_config.minVersion）、提示词相关开关、行为计时参数等。机制上服务端标志可以实时停启本地服务——代码里有现成的执行现场：本地 bridge 服务订阅标志刷新事件，服务端把 tengu_ccr_bridge 门拨到 off，运行中的服务就打日志 [deviceBridge] stopping: the gate turned off 并自停。还有一个已落盘的先例：服务端 API 响应会缓存为本地配置并改变行为（比如 cachedExtraUsageDisabledReason）。

这部分的诚实边界要说清楚：我能证明没有远程强制复活遥测的门控（队列停更是实测，加上架构证据），但不能逐一枚举 700 个标志的全部语义，这层保证只能靠版本重验维持。另有一个与开关无关的通道值得知情：agent 模式下模型输出会被本地执行，若用 --dangerously-skip-permissions 则不再询问。这条防线的性质是模型端对齐，不是操作系统。

防御建议

以下都是自己机器上的合法操作：

# 钉死已审计版本：关自动更新，每次升级前重扫
export DISABLE_AUTOUPDATER=1

# 遥测总闸（含 GrowthBook）：最强单开关
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1

# 或单独关远程标志系统（代价：依赖标志的功能不可用）
export DISABLE_GROWTHBOOK=1

# 运行期监控：哪天它突然开始 ioreg，当场可见
sudo opensnoop -n claude

切换到官方登录之前，先把总闸加上——1P 模式下通道 B 会重新激活。平时可以定期看 ~/.claude.json：device_id 明文可见，字段新增一眼可查。网络出口层面，用你已有的防火墙或代理工具做全流量观测即可；TLS 内容需要自行中间人解密，自行权衡。

方法学边界

这篇审计有四条边界，放在结尾而不是脚注。

第一，时点快照。全部结论绑定 2.1.280 和 2026 年 9 月，自动更新器是活跃的，任何一次更新都可能改变上述一切——这类审计没有一劳永逸。

第二，审计范围。覆盖的是 JS 逻辑区段（155MB，全部应用逻辑所在），字节扫描的零命中只在这个区段内成立；原生 Bun 运行时是理论盲区。不过所有运行时观测与 JS 层逻辑一致，未发现表里不一。

第三，事实与意图分离。本文只陈述有什么代码、往哪发、开关在哪。至于厂商意图，不属于字节能证明的范围。

第四，脱敏。文中的方法与结论不含本人任何凭据、账户标识、节点信息；读者复现时也请注意，不要把自己的 ~/.claude.json 原样贴出来。

表格中的代码实现、门控开关和本机记录是三个不同层面的信息。本文未抓取 TLS 明文流量，出站载荷的字段构成来自请求构造代码与本地队列解码；服务端如何保存收到的数据，本次检查没有验证。
