先说结论

Bun 1.4.0 是 2026-08-20 的 tag。博客把它写成一次「Zig 重写成 Rust」的发布，同时把 1.3.0 之后几个月的功能塞进同一篇文章。我这边全局 bun 还停在 1.3.12，所以对照的是这个版本，不是 1.3.14。

值得升。启动内存几乎腰斩，isbot 那种正则密集路径从不可用变成正常，URL / hex / gzip 明显更快。Image、目录静态资源、Range、bun audit fix、bun pm diff 都能在本机跑通。

但发布博里的倍数不要整表相信。base64url 的 46 倍我没跑出来；await Promise.resolve 相对 1.3.12 几乎持平。macOS 二进制还大了约 2MB，和官方「Linux / Windows 变小、macOS 大约 +1MB」对得上。

怎么测的

1.4 装在独立目录 /tmp/bun-1.4，没有覆盖全局的 1.3.12。同一台机器、同一组脚本，分别丢给三个运行时。

启动用 Python 连跑 30 次取 median / min。RSS 用 /usr/bin/time -l 跑 5 次取最小。微基准是自己写的循环，先预热再计时。功能测试用 bun:test。包管理器用一个最小的 hono + zod + typescript 项目，再另开一个空 workspace 看 isolated linker 默认值。

官方博客覆盖的是 1.3.0 到 1.4.0。你如果已经在 1.3.12，markdown、WebView、Terminal、cron、JSON5、bun run --parallel 其实早就在了。相对 1.3.12，Bun 全局上新冒出来的只有 Image、XML、isStandaloneExecutable。1.4 真正的增量是运行时（Rust、内存、启动）、Node 26、lockfile v2，以及一批包管理命令。

isbot 用的是官方博客里那组 UA、同一个 isbot 5.2.1。1.4 按官方 20 万次循环大约 1.5 秒。1.3.12 按同样规模会把一核打满好几分钟，我中途停掉，改成 N=2000。缩样本之后仍是 209 倍，所以这条不是样本量把戏。

简单 JSON.parse Node 22 还更快（约 9.1µs vs 1.4 的 11.3µs）。runtime 战争没有一边倒。

bun test --parallel：三个各 sleep 50ms 的文件，串行 156ms，并行 73ms。CLI 层的并行是真的。

新 API，点过哪些

下面不是 changelog 摘抄。是本机跑过、有结果的。

Bun.Image

1.3.12 没有这个全局。API 很像 sharp：链式、惰性。width / height 在 metadata() 之前是 -1，我一开始当成 bug，其实是还没解码。

64×64 PNG 走 metadata() 得到正确尺寸，再 resize(32,32).jpeg().bytes()，文件头是 ffd8。HEIC / AVIF / TIFF 官方写 macOS 可用，这次没用真照片压。

Bun.WebView

用 data:text/html 开一个 headless 页，328ms 拿到 document.title === "bun14"，截图 8324 字节。macOS 走系统 WebKit，不用另装 Chrome。这是 1.4 里最「突然多带了一个浏览器」的能力。

Bun.markdown / cron / Terminal

这三项 1.3.12 已经有。Bun.markdown.html("# Hi **world**") 输出带 <strong> 的 h1。官方写明不消毒，javascript: 和事件属性会原样过，当静态站渲染器之前要自己套一层。

Bun.cron.parse("*/15 * * * *") 返回 Date。只接受 5 段（分 时 日 月 周），6 段带秒直接 ERR_INVALID_ARG_TYPE。OS 级 crontab / launchd 这次没注册，避免改这台机器的定时任务。

Bun.Terminal 拉起 bash，写入 echo hello-pty，回显完整。能替一部分 node-pty。

Bun.serve 目录和 Range

"/static/*": { dir } 自动带 etag、last-modified、accept-ranges。Range: bytes=0-4 返回 206，body 是 hello。能替掉一小截 sirv / express.static。

顺手跑了 Hono 4.13.3 文本路由，以及 fetch("https://example.com")，200。bun build 一个两行脚本 3ms，产物 Node 也能跑。

包管理器这块，比运行时更「新」

相对 1.3.12，这些命令是新的，或者第一次好用：

  • 新 lockfile 默认 lockfileVersion: 2，新 monorepo 还有 configVersion: 1
  • 新 workspace 默认 isolated linker。空 monorepo 装完，本机确认出现 node_modules/.bun
  • bun audit / bun audit fix（--dry-run、--latest）
  • bun dedupe --check
  • bun prune --production：dry-run 正确标出可删的 typescript
  • bun pm licenses --prod
  • bun pm diff zod：3.25 → 4.4 给出文件 diff，并标出新增的 node:crypto / vitest import。升级大版本时很好用

现有项目的 hoisted lockfile 会留下旧 linker，升级不会偷偷改 node_modules 布局。新仓库另说。

v2 lockfile 旧 Bun 读不了。Turbo 曾经直接报 Unsupported bun lockfile version: 2，后来有修复 PR。CI 里如果一半人 1.3、一半人 1.4，会炸。

官方「暖安装 7×」要 isolated + 全局虚拟 store + 上千包。这次只装了三个包，2.5 秒，没有资格复述那个 7 倍。

会踩的变更

官方点名五条，本机对上了四条（isolated 只打新 monorepo）：

  1. Node 目标变成 26.3.0，process.versions.modules 是 147。res.writeHeader() 删了，1.3.12 里还在。
  2. 新 monorepo 默认 isolated。
  3. 当 node 跑（symlink / --bun shim）不再自动加载 .env。本机 bun env.js 读到 SECRET，同目录 ./node env.js 是 unset。
  4. YAML 1.2：yes / on / off 是字符串。
  5. TOML / bunfig.toml 更严，非法即 SyntaxError。

另外几条本机或文档对得上、升级前值得扫一眼：

  • fs.rmdir({ recursive: true }) 会抛，改 fs.rm
  • body 读过之后 Response.clone() 抛
  • .xml import 变成文档；runtime .css import 变成 {}
  • Temporal 默认存在，自己 polyfill 可能撞名
  • Bun.cron 用本地时区，不是 UTC
  • bun:ffi 的 cstring 变成普通 string，没有 .ptr
  • HTTP/3 和 fetch({ protocol: "http2"|"http3" }) 仍标 experimental

原生 addon 按 NODE_MODULE_VERSION 137 编的，1.4 要 147。sharp、better-sqlite3、node-pty 这类是高风险。好消息是 Image / Terminal / bun:sqlite 能替掉其中一部分。

Rust 重写，用户侧现在看到什么

1.4 是 Anthropic 收购之后的第一个大版本。Jarred 的 Rewriting Bun in Rust 写得很直：用预发布的 Claude 做了大约百万行移植，动机是 Zig 手动内存和 JSC GC 搅在一起，UAF 和泄漏修不完。

社区吵过这件事。发布还因为 Node 测试套件数字没达标推迟过。我这边只看用户能摸到的东西：二进制里大量 Rust panic 字符串，Zig 编译器特征几乎没了；process.versions.zig 还在，报的是一串 hash。启动 RSS 下来了，isbot 从卡死变成 1µs 量级。Prisma 公开说过 Rust canary 修掉了 Zig 1.3 上的泄漏。

这不证明百万行移植已经「正确」。只说明 1.4.0 作为可运行产物，在这台机器上没有一打开就炸。

该不该升

  • 日常脚本、新项目、已经把 bun 当默认运行时的：升。启动和 RSS 的改善肉眼可见，Image / WebView / pm diff 能少装一堆依赖。
  • CI 钉死 1.3.x、仓库里有 Turbo 或自研 lockfile 解析：CI bun 版本要一起升，接受 lockfile v2 一次 diff。不要一半 1.3、一半 1.4。
  • 依赖 native addon：先看有没有 modules 147 的预编译包，或者改走内置 API。升完立刻跑测试，不要只看 bun --version。
  • 长驻进程：官方数字来自他们自己的生产（Claude Code CPU p99 24%→10%）。本机空服务 RSS 已经降 45%。1.4.0 是重写后第一个稳定 tag，staging 泡几天再全量也合理。

别为了 HTTP/3、7× install、Promise 1.5× 去升。前两个我没在这台机器上证实，第三个几乎没动。
